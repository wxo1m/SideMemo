## 주요 발견

1. **높음 — 웹 저장형 XSS 방어 미흡 (WEB-01)**: `docs/app.js:64`의 clean은 따옴표 없는 이벤트 속성을 제거하지 않는다. 실제 함수에 무해한 `<img src=x onerror=void(0)>`을 입력했을 때 그대로 반환됨을 확인했다. `:157`에서 innerHTML에 삽입한다. 악성 HTML이 자기 메모에 유입되면 해당 브라우저의 로그인 권한으로 실행될 수 있다. 다른 계정에 주입할 수 있다는 증거는 없으며 RLS 우회를 주장하지 않는다. 브라우저에서 스크립트 실행 자체는 검사하지 않았다. 검증된 HTML sanitizer의 허용 목록과 CSP 적용 권고.
2. **높음 — PC 계정 전환 시 데이터 격리 없음 (AUTH-06)**: `sidememo.py:1154,1179`는 로그인/로그아웃 때 메모와 tombstone 및 동기화 상태를 계정별로 분리하지 않는다. `:1229` 이후 upload row는 현재 로그인 user_id를 사용한다. 격리한 실제 build_push_rows 함수에 A의 미전송 메모와 B의 로그인 ID를 넣으면 A 내용의 B 업로드 row가 생성된다. 공유 PC에서 계정 전환 시 개인 메모 유출 가능. 계정별 로컬 저장소와 명시적인 가져오기 절차 필요.
3. **높음 — 업데이트 실행 파일 신뢰 검증 없음 (RELEASE-01/02)**: `sidememo.py:323–350,426`은 URL을 받아 다운로드 후 500KB 초과 여부만 확인하고 실행한다. 출처 허용 목록, 리디렉션 검증, 서명/해시 검증, 최대 크기 제한이 없다. 메타데이터/배포 경로 침해 또는 로컬 임시 파일 교체가 선행되면 코드 실행 위험. 정상 GitHub TLS를 무조건 우회할 수 있다는 뜻은 아니다. 신뢰 가능한 서명 검증과 안전한 임시 경로, 출처 제한 필요.
4. **중간 — 로그인 토큰 평문 저장 (AUTH-04)**: `sidememo.py:119`는 refresh/access token을 JSON으로 저장한다. 원자적 교체는 있으나 DPAPI/자격 증명 저장소 보호는 없다. 같은 사용자 권한의 다른 프로세스가 파일을 읽을 수 있는 경우 세션 탈취 위험. 실제 파일 ACL은 확인하지 않았다.
5. **중간 — 저장 중 편집 유실 가능 (SYNC-02)**: `sidememo.py:1243–1256`, `docs/app.js:240`은 업로드 응답이 도착하면 현재 메모의 변경 여부를 대조하지 않고 synced_at을 설정한다. 실제 confirm_pushed 함수를 격리 실행해 전송 이후 수정도 완료로 표시됨을 확인했다. 메모 revision 또는 전송 payload 비교 필요.
6. **중간 — 백업을 통한 서버 주소/첨부 경로 주입 (DESKTOP-02/03)**: `sidememo.py:1438`의 가져오기는 candidate 전체를 상태로 채택한다. JSON 백업의 attachment 경로는 제한되지 않고 `:1435` 백업 내보내기는 해당 경로의 파일을 포함한다. 백업 settings의 sync_url도 검증 없이 적용되며 세션은 별도 파일에 남는다. 악성 백업을 사용자가 가져온 후 동기화하면 지정 서버에 인증 토큰을 보낼 수 있다. 실제 파일 유출 요청은 수행하지 않았다. 백업 설정 허용 목록, 첨부 폴더 제한, 서버 변경 시 세션 분리 필요.
