# SideMemo 보안 검토 체크리스트

작성일: 2026-11-14 · 대상: Windows 앱, 웹 클라이언트, Supabase, GitHub 배포/업데이트

## 검사 진행 및 판정

1. 현재 커밋, 미커밋 변경, 검토 대상 버전, 실제 릴리스/웹 빌드 버전을 기록한다. 코드와 배포 파일이 동일한지 구분한다.
2. 아래 전 항목을 확인한다. 변경 부분은 집중 검토하되 인증·권한·업데이트 경로를 생략하지 않는다.
3. 코드 검토와 격리된 모의 테스트를 먼저 수행한다. 운영 DB 쓰기, 계정 생성/삭제, 비밀번호 변경, 세션 폐기, 이메일 발송, 부하 시험은 명시적 승인과 테스트 대상이 필요하다. 테스트용 계정 A/B의 비밀번호는 대화나 보고서에 기록하지 않는다.
4. 각 항목은 `통과 / 실패 / 미검증 / 해당 없음`으로 판정한다. 해당 없음에도 이유를 적는다. 접근 권한이나 테스트 계정이 없으면 미검증이며 통과로 간주하지 않는다.
5. 실제 공격 코드는 공개 메모나 운영 DB에 저장하지 않는다. XSS·경로 이탈·손상 파일 검사는 로컬 격리 환경에서 무해한 표식으로 수행한다.
6. 보고서를 `security-reviews/YYYY-MM-DD-review.md`에 저장한다(같은 날은 번호 추가). 이 폴더는 GitHub Pages의 `docs` 밖에 둔다. 보고서 공개/업로드는 별도 요청을 따른다.

## AUTH — 로그인과 세션

- [ ] AUTH-01: 회원가입/로그인 입력, 이메일 인증, 틀린 비밀번호, 만료/변조 토큰을 검사한다. 인증 실패와 네트워크/권한 오류가 구별되고 실패 후 로그인이 성립하지 않아야 한다.
- [ ] AUTH-02: 시간 경과를 모의해 access token 갱신을 확인한다. 새 refresh token이 즉시 안전하게 저장되고 재시작 후 최신 토큰으로 갱신되어야 한다.
- [ ] AUTH-03: 갱신 거절, 누락 토큰, 401, 오프라인, 429, 서버 5xx를 각각 검사한다. 만료 토큰으로 요청을 계속하지 않고 일시적 장애에서는 재시도 가능한 세션을 보존해야 한다.
- [ ] AUTH-04: 저장 실패·디스크 부족·프로세스 중단 시 세션 파일 손상과 성공 오표시가 없어야 한다. Windows 자격 증명/DPAPI 등 토큰 보관 보호와 파일 접근 권한을 확인한다.
- [ ] AUTH-05: 로그인/갱신/동기화/로그아웃 동시 실행, 여러 창/프로세스의 토큰 회전을 검사한다. 로그아웃 뒤 이전 요청이 세션을 되살리지 않아야 한다.
- [ ] AUTH-06: 계정 A에서 B로 전환할 때 메모·첨부·삭제 기록·캐시·진행 중 응답이 섞이지 않아야 한다. 이전 계정의 로컬 메모가 새 계정에 자동 업로드되는지 확인한다.
- [ ] AUTH-07: 비밀번호 재설정/계정 비활성화/서버 세션 취소 후 처리와 인증 리디렉션 허용 목록을 확인한다. 반복 로그인/가입 방어 설정은 설정 조회 또는 로컬 모의로 검토한다.

## DATA — Supabase 사용자 격리

- [ ] DATA-01: notes/settings의 RLS 활성화, USING/WITH CHECK, DB 권한을 확인한다. 로컬 SQL과 운영 정책의 일치 여부는 별도 증거로 기록한다.
- [ ] DATA-02: 익명 요청은 개인 메모/설정을 읽거나 쓰지 못해야 한다. HTTP 상태뿐 아니라 반환 데이터와 실제 변경 여부도 확인한다.
- [ ] DATA-03: 승인된 테스트 A/B로 조회·삽입·수정·삭제·upsert를 검사한다. B의 user_id/note_id를 직접 지정해도 A가 접근하거나 소유권을 바꾸지 못해야 한다. notes/settings 모두 검사한다.
- [ ] DATA-04: Realtime 구독, 첨부 데이터, 삭제 표시, 백업에서도 다른 사용자 데이터가 노출되지 않아야 한다. 브라우저의 user_id 필터만으로 권한을 보장해서는 안 된다.
- [ ] DATA-05: RPC, view, trigger, SECURITY DEFINER 함수, 공개 Storage가 추가되어 있다면 권한 우회와 search_path 설정을 확인한다.
- [ ] DATA-06: 본문/첨부 크기 제한, 데이터 형식 검증, 사용자별 사용량 제한을 확인한다. 과도한 요청이나 대용량 입력은 모의 환경에서 검사한다.

## WEB — 웹 클라이언트

- [ ] WEB-01: 서버 메모 HTML·제목·첨부·클립보드가 DOM으로 들어가는 모든 경로를 확인한다. script, 이벤트 속성, SVG, iframe, 위험 URL 및 인코딩 변형이 실행되지 않아야 한다. 정규식 정화만 신뢰하지 않는다.
- [ ] WEB-02: CSP, 외부 스크립트 버전 고정/무결성, HTTPS, 프레임 삽입 제한, referrer 정책을 확인한다. GitHub Pages에서 실제 제공되는 헤더/정책과 코드 선언을 구분한다.
- [ ] WEB-03: URL/query/hash, 로그, 오류 화면, localStorage, 분석 도구에 토큰이나 메모가 불필요하게 노출되지 않아야 한다. XSS 발생 시 세션 노출 범위도 기록한다.
- [ ] WEB-04: 세션 복원 중 편집/업로드, 새로고침, 로그아웃 후 뒤로 가기, 인증 실패 중 빈 NOTE 생성/업로드를 확인한다. 실패를 빈 서버 데이터로 처리하지 않아야 한다.
- [ ] WEB-05: 외부 링크·이미지·data URI를 통한 추적/정보 유출과 악성 콘텐츠 처리를 확인한다. 사용자 데이터로 임의 서버에 인증 헤더가 전달되지 않아야 한다.

## DESKTOP — PC 저장 및 입력

- [ ] DESKTOP-01: 로컬 메모·세션·로그·백업의 위치와 접근 권한, 평문 저장 여부, 민감 정보 보존 범위를 확인한다. 검사 중 실제 사용자 메모를 열거나 출력하지 않는다.
- [ ] DESKTOP-02: 백업 가져오기에서 경로 이탈(../, 절대 경로), 심볼릭 링크, 압축 폭탄, 손상 JSON, 거대한 첨부를 검사한다. 허용 폴더 밖 쓰기나 사용자 파일 덮어쓰기가 없어야 한다.
- [ ] DESKTOP-03: 첨부 이름·경로·HTML 이미지 참조·외부 링크가 임의 파일 읽기, 삭제, 외부 실행으로 이어지지 않아야 한다.
- [ ] DESKTOP-04: 단축키/단일 인스턴스 IPC/자동 시작/설치·제거 경로의 권한, 인수 인용, DLL 검색 경로를 검토한다. 일반 사용자 동작에 불필요한 관리자 권한이 없어야 한다.

## SYNC — 동기화 무결성

- [ ] SYNC-01: 동시에 편집, 저장 중 재로그인, 재시도, 서버 오류, 삭제와 편집 충돌에서 데이터 유실이나 계정 간 혼합이 없어야 한다.
- [ ] SYNC-02: 업로드 중 추가 편집이 발생했을 때 아직 전송되지 않은 내용을 동기화 완료로 표시하지 않아야 한다.
- [ ] SYNC-03: 원격 payload의 ID·순서·폰트·색·경로·타임스탬프를 신뢰하지 않고 형식과 범위를 확인해야 한다. 잘못된 응답은 기존 메모를 지우지 않아야 한다.

## RELEASE — 업데이트와 공급망

- [ ] RELEASE-01: 업데이트 메타데이터와 파일의 HTTPS 및 허용 호스트/저장소, 리디렉션 검증을 확인한다. 외부 임의 EXE나 저장소 raw fallback으로 잘못된 파일을 실행하지 않아야 한다.
- [ ] RELEASE-02: 다운로드 파일의 신뢰 가능한 해시/서명 검증, 크기 제한, 부분 다운로드 처리, 실행 전 검증을 확인한다. 같은 출처의 해시 비교와 게시자 서명 검증을 구분한다.
- [ ] RELEASE-03: GitHub에서 시험판/초안 표시만 바꾼 경우를 포함해 Pre-release/Draft 제외, 버전 비교, 다운그레이드 방지, version.json과 API 불일치를 검사한다.
- [ ] RELEASE-04: 릴리스 태그·소스 커밋·EXE 내부 버전·설치 파일 해시가 대응하는지 확인한다. 덮어쓴 릴리스는 변경 이력을 남겨야 한다.
- [ ] RELEASE-05: PySide6/Qt/Python/Supabase JS 및 빌드 의존성 버전과 공식 보안 권고를 확인한다. 서명/SmartScreen/백신 오탐은 서로 다른 항목으로 보고한다.

## SECRET — 비밀 및 운영 설정

- [ ] SECRET-01: 저장소·Git 이력·빌드물·로그에서 service_role/secret key, PAT, 비밀번호, 세션 토큰을 검사한다. 발견 값은 마스킹한다. 공개 anon key 자체를 비밀 유출로 판정하지 않되 실제 RLS 검증을 필수로 한다.
- [ ] SECRET-02: GitHub 권한, 배포 토큰 범위, 브랜치 보호, CI 외부 액션 고정, 공개 산출물의 민감 파일 포함 여부를 확인한다.
- [ ] SECRET-03: 인증/동기화 실패 로그가 진단에 충분하면서 토큰·비밀번호·메모를 남기지 않는지 확인한다. 계정 삭제와 백업 보존 정책도 기록한다.

## 결과 보고 형식

- 대상 커밋/버전, 날짜, 검사 환경, 실제 서버 접근 여부
- 항목별 표: ID | 상태 | 근거(파일:행 또는 마스킹된 결과) | 재현 절차 | 영향/심각도 | 수정 권고
- 심각도는 치명적/높음/중간/낮음으로 구분하고 공격 전제와 피해 범위를 근거로 적는다.
- 통과/실패/미검증/해당 없음 개수와 남은 검증 조건
- 실행한 검사와 실행하지 못한 검사, 코드 수정·배포 여부

테스트가 통과해도 “완전히 안전하다”고 단정하지 않는다. 이전에 보고한 문제는 해결 근거가 확인될 때까지 유지한다.
